## 席ごとのモデルの切り分け（施主指示 2026-09-23・ADR 0038）

- 裁定・受理・採点・依頼書と仕様の文言・物語・保護対象の判断 → **設計席自身**（Fable）。
- 実装（1 task = 1 branch = 1 PR）と差し戻し対応 → **Opus 5**（`model: opus`）。
- 現物調査メモ・棚卸し・PNG や出力の比較・実機用 checkout の準備・ペルソナの意見・報告との突き合わせ → **Sonnet 5**（`model: sonnet`）。メモは 300 行以内・疑問 15 件以内。ペルソナは 4 席まで各 150 行以内。
- テスト一覧の照合・差分の列挙・保護対象の差分 0 確認 → **Haiku 4.5**（`model: haiku`）。
- 判断基準は「間違えたとき誰が直すか」。設計席が照合して直せる仕事は下のモデル。差し戻し 2 回目以降は指示を狭く（変更 1 命題・再実行 1 集合）。ローカルの Ollama は Agent から呼べない（別ランナーの補助席で XS / S の task に限り、受理は設計席）。
- **同じ手順を 2 回以上モデルに踏ませたら 3 回目は `eng/` のスクリプト**（chore を実装席に発行・モデル代ゼロ）。スクリプト化した手順は設計席が直接実行し、受理はスクリプトの実出力を読む。最初の候補: #129（実機用 Release の作成と SHA の記録・起動はしない）・#130（保護対象の差分 0 確認・fixture の逐語再利用・scope ごとの checks 数の前後比較）・#131（verify-window の PNG 保存と前後の画素比較）。

## Issue #129 — 実機用 Release の作成と SHA の記録をスクリプトに（実装リナから）

統合単位は draft [PR #133](https://github.com/hideyukiMORI/nene-nib/pull/133)。**draft のまま**（Ready・CI・merge・CLAUDE.md 6 節の更新は設計席）。ブランチ `chore/129-build-release-script` は origin/main `bfa91f0` の上に 2 commit（スクリプト＋conformance / 文書）。本体の作業ツリーで作業し、clean で終わっている。起動中の `build/release-main-123/NeNeNib.exe`（PID 32532）と既定の `build/` には触れていない。

**使い方**: `pwsh -NoProfile -File eng/build-release.ps1 -Ref main`。`build/release-<短い SHA>/NeNeNib.exe` と `out/release/<短い SHA>.json`（SHA-256・ref・commit・HEAD・configure / build / total の秒・道具の版）ができる。**起動はしない**ので、設計席が `Start-Process build/release-<短い SHA>/NeNeNib.exe` で開く。ref 無し・無い ref・dirty な作業ツリーは何もせず終了 1（QLT-013）。ref が HEAD と違うときは `build/worktree-<短い SHA>` を一時的に作って build し、終わったら消す。

**引き継ぐ 3 点。**

1. **SHA は「この 1 回の生成物の印」**である。手で作った `build/release-main-123/NeNeNib.exe` と 978944 バイト中 2 バイト（offset `0x80` の PE `TimeDateStamp`）だけが違い、残りは完全一致した。`/Brepro` は入れていないので、同じ commit を作り直すと SHA はこの 2 バイトぶん変わる。「同じ commit なら同じ SHA」を要求するなら別 Issue（`/Brepro` は link の設定なので ADR 相当）。
2. **ゲートには載せていない**（Issue のとおり・QLT-013）。壊れたことは次に実機用の Release を作るときにしか分からない。引数の検査だけは `tests/conformance` が正例 1・反例 3 で守っている（`python eng/test-conformance.py` 163 tests）。
3. **作業機に残した成果物**: `build/release-bfa91f0/NeNeNib.exe`（main `bfa91f0`・SHA-256 `DE4D3900…59AFC`）と `build/release-1473b2e/NeNeNib.exe`（本ブランチの実装 commit）、記録は `out/release/bfa91f0.json` / `out/release/1473b2e.json`、ログは `out/issue129-main.log` / `out/issue129-head.log`（`out/` と `build/` は追跡外）。hide の実機確認に使うなら `build/release-bfa91f0` が main の版である。

**後続**: #130（保護対象の差分 0 確認・fixture の逐語再利用・scope ごとの checks 数の前後比較）と #131（verify-window の PNG 保存と前後の画素比較）が同じ「2 回踏んだ手順をスクリプトに」の残り 2 本。
