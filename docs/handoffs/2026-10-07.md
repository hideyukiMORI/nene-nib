## この区切りで学んだこと

- **速さを測る間は、同じ機械のほかの席とビルドを止める。** 開始の前に数秒確かめるだけでは足りない（#300 の 1 回目は、測定の途中で別の席がビルドを始めて起動の 3 本が落ちた）。hide がほかの Claude や Codex を動かしていることもある。測る前に負荷を数回読み、hide に「機械が空いているか」も聞く。落ちたら、合格するまで測り直さずに原因を特定し、前提を満たしてから 1 回だけ測る。無効な測定も記録に残す。
- **席に「いまの状態」を試験にさせない。**「基準値がまだ無い」を試験にされ、採用で落ちた（#298）。依頼書に「この工程の後に変わる状態を試験で固定しない」と書く。
- **連ねたコマンドは `set -e` で始め、`| tail` で終了コードを隠さない。** 編集の失敗に気づかず、落ちた試験のまま push した（#298。統合の前に直した）。リポジトリの外の worktree のファイルは、Edit の前に Read が要る。
- **席には worktree の絶対パスで書かせる。** 相対パスで本体の checkout に書いた事故があった（#303 工程 2）。依頼書に明記する。
- **席が設計の穴で止まるのは正しい。** #299（4 行に収まらない関数）・#300（検査を弱めないと書けない替え玉・効いていない安全装置）は、止まって報告されたから設計を直せた。同じ工程の続きは同じ席に答えを送って再開し、main が動いた後のやり直しは新しい席にする。
- **試験を入れると、読んだだけでは分からない破れが出る。** #300 の「`Draw` が callback の失敗を無視する」は、独立レビューでも見つからなかった。
- draft の間の push と Ready が重なると CI が cancelled / skipped になる。`gh run rerun <id>` でやり直すか、最新の実行を `gh run watch <id>` で待つ。
- /design の canvas は、リポジトリの中の `docs/design/<名前>/project/` に `canvas.json` と `.dc.html` を 1 枚ずつ書いて publish する。
