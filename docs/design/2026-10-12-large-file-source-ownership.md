# 大容量本文の所有・読込失敗・保存版の設計案

2026-10-12 / Issue #450 / ロードマップ段階1A。

**状態: 設計案。公開API・所有の変更を受理したADRではない。** hideの「試験は保留して他に着手できるものを着手して」という20:47 JSTの指示に従い、実機試験に依存しない設計を先行する。実装前に下記の未決点を解き、該当ADRと呼出し元の移行範囲を確定する。

基準はmain `843822a`。#442のUTF-8断片保存は統合済み。#446 / [PR447](https://github.com/hideyukiMORI/nene-nib/pull/447)の改行索引は対象契約を確認済みだが、実機性能の有効な集計が得られずdraftのまま保留する。並行負荷だけが原因とは確定していない。今回、その再試行・統合・基準値変更は行わない。

## 解く問題と現行の接続点

2GiBの本文を一つの私有文字列にすると、[事前計画](../plans/2026-10-12-release-scope-and-large-file-probe.md)のprivate bytes増分512MiBという試作条件に収まらない。一方、OSのマップviewを現在の文字列へ単純に置き換えるだけでは、不変性と読み取り失敗を扱えない。

| 現行の正典経路 | いま成立している契約 | 大容量化で必要になる変更 |
| --- | --- | --- |
| `EditorController::read_document` → `FilePort::read` | 同期で64MiB以内の所有bytesを返す。失敗なら新しい文書を採用しない | 要求・完了・取消と、全文を私有メモリに置かない元本文の寿命 |
| `DetectedText::from_bytes` → `TextBuffer::from_utf8` | 外の可変bytesを防御コピーし、文字コード判定と所有を一体化する（ADR 0080） | 分割入力でも同じ検証規則を使い、検証した列と後で読む列を一致させる |
| `TextBuffer` の位置・行・範囲取得 | privateなoriginal/addと索引を持ち、本文の参照はI/O失敗を返さない | 未取得の範囲を表せる契約と、その結果を扱う直接の呼出し元 |
| `replace` → `EditHistory` | 編集前後の文字と戻り位置を履歴へ所有する | 必要な旧本文を得てから一度だけ編集を確定する |
| `write_utf8_document` → `FilePort::write` | 同期呼出し中だけ断片を借用し、同じ一時ファイルへ書いてFlush・置換する（ADR 0119） | 保存要求が不変な版を所有し、その版の必要範囲だけを順に供給する |
| `Win32Worker` / 型付きport | 固定ワーカー1本。空の窓メッセージで知らせ、`collect`で結果を受ける（ADR 0004 / 0062） | 文書・要求・元本文・版を区別し、短い仕事の間に取消と別要求を処理する |

`line_start` / `line_end`だけでなく、`position_of` / `offset_of`、`text_range`、`segments`、`VisualTextView`、Vimの移動・検索・編集、保存が同じ本文を読む。入口一つだけを非同期にして、これらの内部に同期I/Oを隠す案は使えない。Vimの再生単位をまとめる`merge_replayed_edits`にも全文`text()`の呼出しが残り、大容量でのマクロ・ドット反復は別途範囲を定める必要がある。

## OSの事実と設計上の判断

- 読み取り専用のマップはそのviewからの書込を防ぐ。元ファイルから独立した不変スナップショットを意味しない。`FILE_MAP_COPY`はview全体に対するcommit chargeを伴い、今回のメモリ予算を満たす根拠にできない。[MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile)
- ファイルに裏付けされたviewは参照時にも`EXCEPTION_IN_PAGE_ERROR`を起こし得る。Microsoftは対象アドレスを確認した構造化例外処理を求めている。成功したmap作成だけでは以後の参照を成功扱いにできない。[Reading and Writing From a File View](https://learn.microsoft.com/en-us/windows/win32/memory/reading-and-writing-from-a-file-view)
- `CreateFileW`の共有条件は既存handleのアクセスと整合する必要があり、handleを閉じるまで有効。`FILE_SHARE_WRITE`を許さない取得は既存の書込アクセスや書込mappingと競合する。共有削除はrenameも許す。[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- `ReplaceFileW`は置換元と置換先を開き、属性等を引き継ぐAPIである。直前に読んだfile identityとの比較を条件に原子的に置換するAPIではない。**ここからの設計判断として**、事前の同一性比較だけで外部変更との競合を完全に防ぐとは宣言しない。[ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

core/applicationへOSのhandle、map pointer、SEH、隠れた読込callbackを持ち込まない。全コントローラ呼出しを外側のSEHで囲む案も、途中まで進んだ状態やC++の破棄処理を安全に戻す契約がないため、今回の試作候補にはしない。

## 候補比較と次の試作候補

| 候補 | 得られるもの | 解けないこと・費用 | 今回の扱い |
| --- | --- | --- | --- |

| 元ファイルのviewを直接TextBufferへ渡す | 本文全体の私有コピーを避けられる | 外部変更、参照時のI/O失敗、同名置換、失敗しないAPIとの不整合 | そのままの接続は見送る |
| 私有の退避ファイルを作り、そのviewを直接渡す | 元パスが変わっても旧本文を保持できる | 参照時のI/O失敗は残る。退避のディスクと時間も必要 | 所有の分離だけでは不十分 |
| **私有の退避ファイル＋adapterでの範囲読込＋所有する不変の取得範囲** | I/O失敗をportの結果に閉じ、coreに成功済みbytesだけ渡せる | 全文退避の時間・ディスク、取得範囲の予算管理、本文取得APIと呼出し元の移行が必要 | **次に小さく成立性を調べる候補** |

最後の案は採用決定ではない。まず通常の範囲ReadFileで失敗境界を確認し、マップは必要性が分かった段階でadapter内の読込手段として比較する。マップを試す場合も、参照と所有領域へのコピーをadapter内で完了し、viewを中核へ漏らさない。FR-013のメモリマップ方針を、この設計案だけで削除・変更しない。

私有の退避ファイルは一時的な作業資源であり、自動復旧用の新しい保存形式とはしない。製品での配置先・容量制限・異常終了後の回収は実装ADRで定める。試作の入力・退避・出力はD:/NeNeNib配下に限定する。

## 所有と寿命の案

| 値・資源 | 所有者と寿命 | 禁じる取り違え |
| --- | --- | --- |
| 元本文の識別子と検証結果 | applicationが文書の寿命に結び付ける。coreにはOS非依存の識別子・長さ・検証済み範囲を渡す | file pathや現在のタブ位置を本文の同一性に使わない |
| 退避ファイルとhandle | adapter。文書と進行中の要求からの利用がなくなってから解放する。close要求と仕事の終了を照合する | core値のコピー・破棄を隠れたファイル操作にしない |
| 編集後の本文とundo/redo | application所有の一つのTextBufferと履歴。original/addのpieceという意味を維持する | 大容量専用の第二の本文・Vimエンジン・undoを作らない |
| 取得済み範囲 | 境界で防御コピーして所有する不変bytes。元本文の識別子と範囲に結び付け、applicationが予算と採用を管理する | 外から保持できる可変pointerや、検証フラグと別bytesの組合せを公開しない |
| 進行中の操作 | applicationが文書ID、要求ID、要求時の版、必要範囲を保持。adapterへ不変の要求を送る | 別タブや別版の完了を現在の選択へ適用しない |
| 保存要求 | 保存対象の版・保存先・文字コード・配置modeと、本文資源の寿命を保持する | 借用`string_view`列だけをキューに置かない |

元本文は開くときに一度退避し、局所編集や保存のたびに全文退避を作り直さない案とする。通常の保存成功でundoを消したり元本文を差し替えたりしない。元本文の整理・再基底化が必要になった場合は、履歴と全参照の移行を別に設計する。

退避の生成中は元本文IDを公開しない。完成時にadapter側の資源を封印し、以後の書込要求を受け付けず、外から書き換えられない共有条件と所有を保つ。資源を同じpathで開き直すだけで同一とみなさず、検証したbytesと取得元の結び付きを維持する。この封印と解放を型でどう表すかも単位1〜2で定める。

現行のadd chunkはprefixを変えず追記するが、`TextBuffer`をコピーするだけでワーカーとの並行読みに安全になるとはいえない。保存へ渡すadd領域の凍結、以後の追記先の分離、元の借用の禁止をADRで決め、対象の並行契約を確認するまで非同期保存を接続しない。

## 読込・操作の状態遷移案

1. **準備中**: adapterが元ファイルを一度開き、書込・削除を許さない共有条件で退避を作る候補から始める。既存writerと競合したら取得失敗として返し、共有条件を緩めて続行しない。これは通常の共有アクセスを前提にした案であり、あらゆるファイルシステムのsnapshot保証とはしない。
2. **検証中**: 有界のブロックを退避しながら既存UTF-8判定を分割入力へ拡張した一つの検証器へ渡す。最大3 bytesの未完コードポイント、先頭BOM、CR/LF境界、NUL、末尾の未完入力を扱う。ブロックごとに別の文字コードを推定しない。
3. **公開可能**: 宣言された全bytesの取得・検証と必要な索引の準備が成功して初めて新しい文書へ置き換える。最初の試作では全文検証前の部分本文を製品のTextBufferとして公開しない。先頭表示までの時間が長くなる可能性は測定に残す。
4. **範囲待ち**: coreの純粋な処理が必要範囲を要求として返し、applicationが取得を手配する。欠けたbytesを空文字やNULで代用しない。描画は最後の成功した表示値を保持し、待機中に別タブへ移れるようにする。
5. **確定**: 文書ID・要求ID・元本文ID・版が一致する成功結果だけを使って、状態遷移を一度行う。編集に必要な削除前の本文や履歴を準備できなければ、本文・選択・履歴を部分更新しない。
6. **取消・失敗**: 要求を無効にし、以後の完了は資源解放だけに使う。元の文書・未保存本文・undoを保持する。待機中に受けた同じ文書への鍵を無断で再解釈しないよう、順序・取消・上限の契約を実装ADRで定める。

これは公開APIの名前や型を決めたものではない。特に「範囲要求を返す→取得済みの不変入力で再開する」を、Vimの複合操作や文字列検索へどう渡すかは次の設計課題である。内部で隠れて同期readする便法や、成功するまで操作全体を無制限に再実行する便法は採らない。

UTF-8検証に失敗した大容量入力を、直ちに「壊れたUTF-8」と断定しない。Shift_JISである可能性と、試作が大容量UTF-8に限定されることを結果として区別する。小さい既存入力の判定優先順・Shift_JIS変換を維持し、分割版と全文版で検証規則を二重化しない。BOMは退避bytesに保持し、論理本文の先頭から除く位置と保存時の1回だけの付加を明示する。

## 保存と外部変更

保存は同じFilePortの一時ファイル→全書込→Flush→配置という意味を維持する。範囲供給の追加では、保存の実装口とすべての呼出し元を同じ変更で移行する。旧同期処理と大容量専用処理を独立した実装として残さない。

- 保存開始時に編集単位を閉じ、不変な本文版と、その版に結び付く保存地点を取得する。進行中の本文が変わっても保存要求をすり替えない。
- 完了した保存は、実際に保存した版だけを保存済み地点にする。保存中にundo後の分岐が生じた場合、数値の履歴positionが同じという理由で別の本文を保存済みにしない。履歴との同一性を持つ保存地点の設計が必要。
- 読込・書込・Flush・配置が失敗したら成功結果を返さず、未保存の本文を保持する。退避の読み出しに失敗しても、不完全な内容で保存先を置換しない。
- 外部から元パスが書換え・置換・削除されても、成功済みの退避と現在の編集版は変えない。外部変更の通知や再読込の選択は別の利用者操作とする。
- 同名保存前に記録したfile identity等との変化を検出した場合の扱いを決める。ただし、比較と置換の間の競合は未解決。競合を防げたと宣言する前に、handle共有と置換の契約を確かめる。現在の置換動作より強い外部変更保護をこの文書で保証しない。

**取消の境界**も必要。配置を始める前の取消では元ファイルを保持する。配置が成功した後に取消が届いた場合は「保存していない」と返さず、保存済み版を含む完了として回収する。閉じたタブへの古い完了は現在のタブを変更せず、配置の結果と資源解放を扱う。

配置APIの途中失敗は、本文の未保存状態とディスク上の配置結果を分けて記録する。`ReplaceFileW`には失敗の種類ごとにファイル名や属性の残り方が異なる説明があるため、一律に「何も変わっていない」とは返さない。失敗直後に自動で再試行・一時資源削除を行う範囲は、既存実装との差とともに保存ADRで見直す。

## メモリ・仕事の区切り

#446の提案表現では2GiBのbitmapと累積数のpayloadは合計288MiBで、512MiBとの差は224MiB。これは測定値ではなく表現からの計算であり、vector容量・allocator・索引の版の重複・退避読込・防御コピー・編集履歴・文字組み・ワーカー結果は別に数える。未受理の索引を前提に性能成立とは判断しない。

範囲取得・防御コピー・結果待ち・画面使用中のすべてを同じメモリ予算へ含める。読み出しは試作開始値として1MiB以下の仕事へ区切る案にし、64KiBの論理行と8MiBの長行は別に評価する。1MiBへの分割だけでは、OS I/OやFlushを100ms以内に取消できる証明にならない。固定ワーカー1本の待ち方・OS取消と回収を確認する。

最初の試作は全文検証・索引の完了後に本文を採用する候補とする。遅延索引や検証済みprefixの先行表示を追加する場合は、未確定の行数・末尾移動・符号化判定・取消を別の状態として設計する。未知の末尾を現在のEOFとして扱わない。

2GiBの退避に加え、保存時は別の一時ファイルと既存の保存先が同時に存在する。メモリを減らした費用がディスクと初回読込へ移ることを記録し、空き容量・確保失敗・異常終了後の回収方針を試作前に確定する。ディスク不足の実測のために実ディスクを満杯にしない。

## 実装へ切る順序と未決点

2026-10-13: 単位1の分割UTF-8は#452 / PR453で機能契約確認済み、性能未受理。読込完了の境界は性能確認と独立に#463 / [ADR0124](../adr/0124-file-read-completes-the-declared-size.md)へ切り出した。既存同期readの短い成功を残り取得へ進め、宣言長が揃う前の0進捗/失敗を `unreadable` にする。これは退避資源・非同期read・2GiB対応の受理ではない。

単位2はOS資源境界だけを確かめるもので、別のpiece tableを持つ試作エディタではない。単位3は全利用箇所へ影響するため、APIを先に足して使われないまま残す実装は始めない。小さいファイルの退行、8MiB長行、巨大な削除/貼付/マクロの上限も移行の前に区別する。初版の範囲を狭める必要が出たら根拠をhideへ示して判断する。

小さい入力で先に確認する境界は次に絞る。表は初期計画で、#452/#463/#465の実施状況は各品質記録と[current](../todo/current.md)を参照する。小さい入力の結果は2GiBの試験計画の代替ではない。

| 入力・事象 | 必要な観測 |
| --- | --- |
| UTF-8の2/3/4 bytes文字、BOM、CRLFを各読込境界で分割 | 同じbytesを一度で渡した場合と判定・本文位置・改行が一致。最終未完入力を拒否 |
| 宣言サイズより短い成功read、途中のread失敗 | 不足分を読んで完了するか型付き失敗。短縮した本文を完成した文書として採用しない |
