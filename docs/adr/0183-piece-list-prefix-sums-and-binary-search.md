# ADR 0183 — piece の列は累積の長さと改行の数を持ち、読む口は二分探索で引く（段 1）。塊の列は次の段

- 状態: 受理（設計席の決定・2026-11-12・#1474 の下ごしらえ G3 の実測から）・段 0 と段 1 は #1474 で実装
- 日付: 2026-11-12
- Issue: #1474（調査は #1451 / #1473・ADR 0180 の「残る穴」）
- 規則: ARC-001 / ARC-003 / ARC-005、CPP-002 / CPP-005 / CPP-011、CNF-009、QLT-014、ADR 0044（add バッファの chunk の列）/ 0047（改行の索引の共有）/ 0121（改行の索引の疎 / 密）/ 0139 / 0140（仮想桁の部分和）/ 0180（履歴の塊・piece の列の共有）

## 文脈

ADR 0180 で状態の写しは piece の列を複製しなくなったが、編集 1 回が列を作り直す費用は piece の数 P に比例したまま残した（#1474）。下ごしらえ G3 が測ると、**一番大きいのは読む口だった**（`D:/NeNeNib/outputs/20261112/1474/groundwork.md` を `docs/quality/piece-list-cost-2026-11-12.md` に写す・混んだ機械なので比で読む）。

- `text_range` `line_start` `line_end` `position_of` `offset_of` は、どれも piece の 0 番目から線形に歩く（累積の長さが無い）。40 行ぶんの読みは P = 1k / 4k / 16k / 64k で 0.29 / 1.2 / 5.6 / 27 ms。
- `replaced` 1 回は同じ P で 30 / 57 / 504 / 4,315 µs（前後の piece を写し、構築子が合計を出すためにもう 2 周する）。
- 行を短いまま `I#<Esc>j` で P を約 16k にすると、frame 1 枚が 10.1 ms・編集しない `l` `h` が 1 鍵 0.84 ms（1 打鍵の基準値 0.64 ms を超える）。frame 1 枚で約 290 回、1 鍵で約 24 回、列を歩いている。
- piece は「5 文字打って BS」1 周に 1 つ、行頭への貼り付け 1 回に 2 つ増える。undo / redo も増える側。打つだけなら増えない。
- 「すべて置換」10 万か所は、前の P が 1 なら 221 ms、8k なら 6.8 s（O(行数 × P)）。

長く編集した文書ほど、打鍵と描画が遅くなる。

## 決定

1. **#1474 の範囲を読む口まで広げ、読む口を先に直す（段 1）。** 効果が一番大きく、変更が小さい。
2. **piece の列は、各 piece の手前までの累積の長さ（バイト）と累積の改行の数を持つ。** 列を作る 1 か所（構築と `replaced`）が 1 周で埋める（合計のための余分な 2 周をやめる）。列は今までどおり不変の束（`shared_ptr<const>`・ADR 0180）で、値の意味と公開の口は変えない。
3. **読む口は二分探索で引く。** 位置 → piece（`text_range` `position_of` `offset_of`）は累積の長さで、行 → piece（`line_start` `line_end`）は累積の改行の数で引いてから、今の改行の索引（ADR 0047 / 0121）で piece の中を引く。0 番目から歩く道を残さない（引く口は `TextBuffer` の中の 1 本の helper）。
4. **覚え（cache）は持たない。** 「直前に引いた piece を覚える」形は `mutable` が要り、不変の値とスレッド 1 本の前提（CNF-009）を崩すので採らない（下ごしらえの案 C の位置の覚え）。
5. **段 0 を同じ PR に入れる**: `nib_perf_probes` に probe（`piece-read-after-{1000,4000,16000}-pieces`・`piece-replace-after-{…}`・`replace-all-100000-after-8000-pieces`）を足し、性質の試験 `--text-buffer-property` に P が数千で「古い値の分岐（写しの後に両方を編集する）」を踏む組を足す（今は P が数十までしか届かない）。
6. **次の段（別の PR）**: 段 2 = piece の列を塊の列にして `replaced` は当たった塊だけを作り直す（下ごしらえの案 B・塊は 256 件前後・ADR 0180 の履歴と同じ形）。段 1 の実測の後に、塊の大きさと割る / 合わせるしきい値を決める。段 3（add の列と仮想桁の索引の写し）と段 4（隣り合う piece の併合）は別の Issue。永続の木（案 A）は、塊の列で足りないと実測で分かったときに塊の列から育てる。
7. **受け入れ**: 静かな機械で 8 本のゲート（QLT-014）が 0 regression（空の文書の 1 打鍵 0.64 ms・16 MiB で 200 打鍵 2.34 ms を悪くしない = P の小さい文書に二分探索の定数を足さないこと）・probe が P = 16k の読みで桁の改善を示す・性質の試験と fixture 全件が不変。

## 強制

- **active**: 性質の試験 `--text-buffer-property`（`tests/unit/TextBufferPropertyTests.cpp` の「piece が数千の本文」・既定実行の契約に載る）。「5 文字打って BS」の周・行頭への貼り付け・短い削除・undo / redo の入れ直しを 2,400 段と 800 段（CRLF）積み（piece は約 2,100 と約 780）、毎段で素朴な `std::string` の模型と読む口を照合し、16 段に 1 回は全文と 3 行の標本、200 段ごとに仮想桁の索引まで含めた全部の照合をする。97 段ごとに写しを取って写しと元を別々に編集し（どちらを先にするかを入れ替える）、写しは最後にもう一度照合する。`--editing-property` `--edit-history-property` も同じ口を通る。
- **構造（機械の検査は無い・守るのは上の性質の試験と独立レビュー V-1562 の変異 6 つ）**: 位置 → piece と 行 → piece を引く口は `TextBuffer` の private の `piece_at` と `piece_of_newline` の 2 本で、範囲を歩く道はどれも `pieces_from`（`piece_at` から始まる列の尾）から始める（`src/core/TextBuffer.cpp`）。累積を埋めるのは列の末尾に piece を置く `placed` の 1 か所で、列を作る周（構築・`collect`・挿入）の中で埋める（別の周を回さない）。0 番目から歩くのは本文の全部を読む `segments` と `longest_line_bytes` と、`replaced` の前半の `collect(0, from)` だけ。
- 記録だけ: probe `piece-read-after-{1,1000,4000,16000}-pieces`・`piece-replace-after-{…}-pieces`・`replace-all-100000-after-{1,8000}-pieces`・`frame-after-{1,16000}-pieces`（`nib_perf_probes`・ゲートの必須にしない・ADR 0138 と同じ扱い）。前後の比は [記録](../quality/piece-list-cost-2026-11-12.md) の末尾。
- 決定 7 の受け入れ（静かな機械の 8 本のゲート）は設計席がまとめ枝で測る（この ADR の実装の PR では測っていない）。

## 帰結

- 読む口は O(log P)。`replaced` は O(P) のまま（定数は約 1/3: 余分な 2 周が無くなる）。
- piece 1 つにつき累積の値 2 つ（16 バイト）が増える。

## 残る穴

- `replaced` の O(P) と「すべて置換」の O(行数 × P)（段 2）。add の列の写しと仮想桁の索引の読み直し（段 3）。
