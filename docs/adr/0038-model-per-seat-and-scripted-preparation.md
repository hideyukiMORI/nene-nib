# ADR 0038 — 背景席は仕事の種類でモデルを明示し、繰り返す下ごしらえはスクリプトにする

- 状態: 受理（施主指示 2026-09-23。次のセッションから実行）
- 日付: 2026-09-23
- Issue: #128
- 影響する規則: QLT-001 / QLT-012 / QLT-013 / GIT-001〜004

## 文脈

このリポジトリでは設計席（Fable・最上位モデル）が Issue と ADR と依頼書を書き、背景席（Agent）が実装・実測・限定検証・文書・draft PR を担う（[ADR 0021](0021-diff-scoped-verification-and-result-reuse.md) の検証方針・引き継ぎの「運用の約束」）。2026-09-22 までは背景席をすべて Opus 5 で立てていた。hide の指示（2026-09-23）: **Opus 5 の消費が速い。原因は判断を含まない仕事まで Opus 5 に出していること。** 席ごとにモデルを落とし、同じ手順を 2 回以上モデルに踏ませたら 3 回目はスクリプトにする。

hide の指示は複数のリポジトリに共通の型で書かれている。NeNeNib に無い語（mailbox・golden / replay・launcher・`tools/`）は本 ADR の読み替え表で Nib の対応物に写す。

## 決定

**背景席を立てるときは仕事の種類で `model` を明示する。判断基準は「その仕事を間違えたとき誰が直すか」で、設計席が照合して直せる仕事は下のモデルでよい。同じ手順を 2 回以上モデルに踏ませたら、3 回目は `eng/` のスクリプトにして設計席が直接実行する。**

1. **席とモデル**

   | 仕事 | 席 | モデル |
   | --- | --- | --- |
   | 裁定・受理・採点・依頼書と仕様の文言・物語・保護対象（期待値・生成物・基準値・schema・ゲート）の判断 | 設計席自身 | 最上位（Fable） |
   | 実装（1 task = 1 branch = 1 PR）と差し戻し対応 | 実装席 | Opus 5（`model: opus`） |
   | 下ごしらえ: 現物調査メモ・棚卸し・PNG や出力の比較・実機用 checkout の準備・ペルソナの意見・報告との突き合わせ | 下ごしらえ席 | Sonnet 5（`model: sonnet`） |
   | 純粋な機械作業: テスト一覧の照合・差分の列挙・保護対象の差分 0 確認 | 機械作業席 | Haiku 4.5（`model: haiku`） |

   `model` を省いて既定（Opus）に落ちる立て方はしない。依頼書の冒頭に席とモデルを書く。
2. **量の上限**: 下ごしらえのメモは 300 行以内、疑問一覧は 15 件以内。ペルソナは 4 席までを Sonnet で、各席 150 行以内。
3. **差し戻し**: 2 回目以降は指示を狭くする（変更 1 命題・再実行 1 集合）。
4. **Ollama**: ローカルの Ollama は Claude Code の Agent からは呼べない。使うなら別ランナーの補助席として XS / S の task に限り、受理は設計席が行う。
5. **繰り返しはスクリプトに**: 同じ手順を 2 回以上モデルに踏ませたら、3 回目は `eng/` のスクリプトにする chore を実装席に発行する（モデル代ゼロ）。スクリプト化した手順は下ごしらえ席に頼まず設計席が直接実行し、受理の独立照合はスクリプトの実出力を読む形にする。最初の候補 3 つは Issue #129（実機用 Release の作成と SHA の記録・起動はしない）・#130（保護対象の差分 0 確認と fixture の逐語再利用・scope ごとの checks 数の前後比較）・#131（verify-window の PNG 保存と前後の画素比較）。
6. **読み替え表（Nib）**

   | 指示の語 | NeNeNib での対応物 |
   | --- | --- |
   | `tools/` | `eng/`（[PROJECT_LAYOUT](../PROJECT_LAYOUT.md)） |
   | 保護対象 | `tests/vim/fixtures.json` の期待値・`VimFixtures.hpp`・`eng/perf-reference.json`・`eng/symbol-allowlist.json`・`eng/conformance-rules.json`・保存 schema・ゲートの閾値 |
   | golden / replay のフィールド単位の照合 | fixture の逐語再利用（削除行は metadata 2 行だけ）と scope ごとの unit checks 数の前後比較 |
   | mailbox | 無し。依頼書は scratchpad、報告は Agent の完了報告と `SendMessage` |
   | 実機用 checkout の準備 → launcher の次回先 | `build/release-<短い SHA>/NeNeNib.exe` を作って SHA を記録する。起動は設計席が `Start-Process` で行う |
   | 保護対象の差分 0 確認 | 上の #130 のスクリプト。それまでは機械作業席（Haiku） |
7. **記録**: 引き継ぎに 1 節、`docs/todo/current.md` の先頭に 1 行。依頼書（scratchpad）の型に「席・モデル」の行を足す。

## 強制

- 背景席の `model` の明示: **planned**（レビュー事項。Agent の呼び出しはリポジトリの外なので機械で守れない。依頼書と引き継ぎに席とモデルを書き、日報で振り返る）
- スクリプト化の候補が Issue になること: **planned**（引き継ぎの「同じ手順を 2 回踏んだ」の記録から設計席が発行）

## 結果

得られるもの: 判断を含まない仕事が Sonnet / Haiku に落ち、Opus 5 の消費が実装だけになる。繰り返しの手順がスクリプトになり、受理が実出力の照合になる。
失うもの・残る穴: 下ごしらえ席の出力は設計席が照合する前提なので、設計席の読む量は増える（上限で抑える）。機械で守れない約束が 2 つ増える。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| すべての背景席を Opus 5 のまま | 消費が速い（施主指示の背景） |
| 実装席も Sonnet に落とす | 実装を間違えたときに直すのは実装席自身で、設計席が照合して直せる量ではない。差し戻しが増えて逆に高くつく |
| スクリプト化を下ごしらえ席に頼む | 手順そのものは決まっていて判断が無い。実装席の chore として 1 PR で入れ、以後はモデル代ゼロ |
