# ADR 0039 — 実装席は工程ごとに新しい席にし、道具の出力を小さく保つ

- 状態: 受理（施主指示 2026-09-23・手 3。次に立てる Opus の実装席から実行）
- 日付: 2026-09-23
- Issue: #136
- 影響する規則: QLT-001 / QLT-012 / GIT-001〜004
- 前提: [ADR 0038](0038-model-per-seat-and-scripted-preparation.md)（手 1: 席ごとのモデル・手 2: 繰り返しはスクリプト）。本 ADR は手 3 で、0038 の表を置き換えない

## 文脈

hide の指示（2026-09-23・複数リポジトリ共通の型）。9/22 の Claude Code の transcript（`~/.claude/projects/<repo>/**/*.jsonl` の assistant `usage`）を集計した実測:

- 減っているのは **Opus 5 の枠**で、設計席の Fable とは別の財布。
- Opus 5 の消費は全部が Agent の実装席。1 席あたり 150〜400 ターン、文脈が 350〜800K まで太ったまま毎ターン読み直し、cache read が 1 席 0.4〜1.7 億トークン。
- 費用は「ターン数 × その時点の文脈長」の積み上げなので、**太った席を長く走らせるほど二乗で効く**。
- 9/22 の Opus 起動 108 本のうち約半分がレビュー・ペルソナ・棚卸し・スクリーンショット撮影・checkout 準備で、手 1（ADR 0038 の表）が守られていなかった。

モデル階層（手 1）では減らない。実装席の形を変える。

## 決定

**1 task を 1 席で走らせない。実装席は工程ごとに新しい Agent にし、道具の出力を小さく保ち、task を S 級に切る。枠の減りは transcript の数字で言ってから手を選ぶ。**

1. **席の分割（3-1）**: probe（現物調査）→ 実装 → 差し戻し対応を、それぞれ**新しい Agent** にする。引き継ぎは報告ファイル（scratchpad か `docs/`）で渡す。**Opus の席を `SendMessage` で次の仕事に使い回さない**。`fork` は親の全文脈を継ぐので背景席に使わない。429 で止まった席を「続きを」で再開するのは同じ工程の中だけ（ADR 0038 の教訓 (1) はこの範囲で残す）。
2. **道具出力を小さく（3-2）**: 文脈が太る原因はテスト全文・ビルドログ・ファイル丸読みが毎ターン残ること。実装席の指示書の型に次を入れる。
   - テストは対象だけ実行し（`ctest -R` / `nib_tests.exe` の対象指定）、失敗行だけ `tail` する。
   - ビルド・ゲートのログは `out/` のファイルへ落とし、`grep` / `Select-String` で読む。
   - ファイルは必要な範囲だけ読む（`Read` の offset / limit・`sed -n`）。
   - 最終報告は **30 行以内**。詳細は報告ファイルに書き、親にはパスと数字だけ返す。
3. **task を小さく（3-3）**: M 級 1 本より S 級 3 本。差し戻しは「変更 1 命題 = 新しい席」（ADR 0038 決定 3 の「狭く」を席の単位でも守る）。
4. **手 1 を守る（3-4）**: レビュー・ペルソナ・棚卸し・スクリーンショット撮影・実機用 checkout の準備は Sonnet / Haiku（ADR 0038 の表）。Opus は実装と差し戻し対応だけ。
5. **Opus 5.5 は試行（3-5）**: API 単価は Opus 5 より低く同じトークナイザだが、サブスクの週間枠での重み付けは未確認。実装席で 1 日走らせ、枠の減りを見てから決める。Agent の `model: opus` がどの版に解決されるかは transcript の `model` の欄で確かめる（設計席が読む）。
6. **計測して言う**: 枠の減りを疑ったら、transcript の `usage`（`cache_read_input_tokens` / `output_tokens` / 最大文脈 / ターン数）を席ごとに集計してから手を選ぶ。数字で言えないうちは手を増やさない。集計は手で 1 回踏んだので、2 回目で `eng/` のスクリプト候補（ADR 0038 決定 5・未起票）。
7. **読み替え表（Nib・ADR 0038 の表への追加）**

   | 指示の語 | NeNeNib での対応物 |
   | --- | --- |
   | 引き継ぎ書の手 1・手 2 の節 | [引き継ぎ 2026-09-23](../handoffs/2026-09-23.md) の「席ごとのモデルの切り分け」 |
   | 正本の `next_actions` の先頭 | `docs/todo/current.md` の「現在の Issue」の先頭行 |
   | 実装席の指示書テンプレート | [`docs/templates/implementation-seat-brief.md`](../templates/implementation-seat-brief.md)（依頼書の型。scratchpad に写して埋める） |

8. **記録**: 引き継ぎに 1 節、`docs/todo/current.md` の先頭に 1 行、依頼書の型に 3-1・3-2 の文言。日報で「席の本数・工程・最終報告の行数」を振り返る。

## 強制

- 工程ごとの新しい席・`SendMessage` の使い回し禁止・`fork` 不使用: **planned**（Agent の呼び出しはリポジトリの外。依頼書の冒頭に「席・モデル・工程」の行を書き、日報で振り返る）
- 道具出力の上限・最終報告 30 行: **planned**（依頼書の型に文言として置く。守られたかは設計席が完了報告の行数で見る）
- transcript の usage の集計: **planned**（スクリプト化は未起票）

## 結果

得られるもの: 1 席の文脈が工程の長さで止まり、cache read が「ターン数 × 文脈長」の二乗で伸びなくなる。差し戻しが新しい席になるので、失敗した席の文脈を引きずらない。
失うもの・残る穴: 工程の境で設計席が報告ファイルを読んで次の依頼書を書く手間が増える（30 行の報告と報告ファイルの分離で抑える）。probe の席の知見は報告ファイル経由でしか実装席に渡らないので、報告ファイルの質が実装の質を決める。Opus 5.5 の枠の重みは 1 日走らせるまで分からない。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 手 1 の徹底だけで様子を見る | 9/22 の実測で Opus の消費は実装席そのもの。モデル階層では減らない（施主指示の背景） |
| 実装席の文脈を `compact` で切り詰めて同じ席を続ける | 要約の質を設計席が確かめられない。報告ファイルで渡すほうが正本が残る |
| 1 task を 1 席で走らせ、道具出力だけ小さくする | 差し戻しの往復が同じ席に積もる。二乗の項は席の長さなので席を切るのが先 |
