# ADR 0069 — 表示中の本文の文字組みを描画器が再利用する

- 状態: 受理
- 日付: 2026-10-04
- Issue: #291
- 影響する規則: FR-012 / FR-015 / FR-017 / D12 / D14 / D15 / ARC-001 / ARC-004 / ARC-007 / ARC-011 / CPP-011 / CPP-012 / CPP-016 / QLT-001 / QLT-012 / QLT-013 / QLT-014

## 文脈

#290のsplit試作で、1行6217 bytesの日本語文書は単画面でも1文字入力から提示まで約326msだった。
#291で既存のTimingPortを通る一時的な計測点を置いた。1280×800 / DPI 120 / Cascadia Code 13.5ptで空文書と同じ日本語文書を各3回、固定回数で測った。
日本語の中央値は325.999msで、19行のDrawTextLayout呼び出しが322.712ms、frame生成0.705ms、提示前の待機0.001msだった。
別の計測版でGetMetricsを描画前に呼ぶと、文字組みを含むlayout生成へ311.463msが移り、DrawTextLayoutは9.890msとなった。
したがって今回の主因は、同じ表示行でも毎回layoutを捨てて文字組みをやり直すことにある。

ADR 0009の決定6は、測定で必要と分かるまでは各行のlayoutを毎回作るとしていた。今回の測定をその必要性の根拠とする。
DirectWriteのlayoutは字形の位置を保持し、同じlayoutの再使用で再計算を避けられる（[Microsoftの説明](https://learn.microsoft.com/en-us/windows/win32/direct2d/direct2d-and-directwrite#drawtextlayout)）。
これは字体や文字の範囲を変える設計ではない。D12 / D14 / D15の表示と入力の仕様を維持する。

## 決定

1. **所有者はDirect2DRendererのまま**。本文のlayoutだけを再利用する。本文・履歴・選択・IME・カーソルの正本は移さず、core / applicationに描画資源やキャッシュ状態を足さない。
2. **入口は既存のlayout_ofだけ**。通常の行、IMEの文字を差し込んだ行、クリックの桁判定が同じ入口を通る。未登録なら従来のtext_layoutで全文を組む。文字数や推定幅で切らず、結合文字・Tab・双方向の文字・フォントfallbackをDirectWriteへ渡す範囲を保つ。
3. **キーは表示文字列の全体とlayoutの幅・高さ**。行番号や文書番号では引かない。行の挿入、スクロール、タブ切り替えでも、文字列と幾何が一致する資源だけを使う。IMEでは差し込み済み文字列をキーにする。
4. **保持は現在と直前の描画に限る**。描画開始時に現在の列を直前の列へ移し、一致する資源を現在の列へ移す。同じ描画内の一致は現在の列から読む。描画終了時に直前の残りを捨てる。文書全体や過去の画面を蓄積しない。クリックは表示行の同じ入口を使う。
5. **本文の書式が変われば全て捨てる**。フォント名・サイズ・DPIを反映したbody formatの生成成功時に両方の列を消す。幅・行高の違いはキーで区別する。deviceの作り直しでは描画器と一緒に破棄される。テーマ、選択、検索、キャレットの色や矩形は各回従来どおり描き、layoutに保存しない。
6. **本文以外は対象にしない**。右寄せやコマンド入力はlayoutの整列・高さを生成後に変えるため、この再利用へ混ぜない。全描画を別の描画器へ移す道や機能スイッチを足さない。
7. **測定用の変更を製品へ入れない**。一時的な節目・容量拡張・GetMetricsの先行呼び出しは隔離したprobeの束へ保存する。製品の速度は追加計測点のないReleaseで比較する。既存の速度基準値と#290のsplit採用条件は変えない。

## 検証の範囲

- cacheのキーと破棄で変わり得る本文を対象に、編集・行移動・スクロール・選択・検索・クリック・幅・フォント・IMEの表示を確認する。変更前後の画素を比較し、再利用で古い文字や幾何が残らないことを調べる。
- 空文書、短行の16MiB文書、同じ長い日本語行を通常版同士で比較する。成功済みの描画・入力の検証は、関連実装が不変ならPR・mergeで再使用する。
- 改善後の同じ表示値を使う2枠試作を再比較する。別文書のframe生成や状態所有の移行は引き続き未検証で、split製品採用はこの変更だけで決めない。

## 限界

初めて見せる行と編集された長い行は全文の文字組みが必要であり、その費用は残る。描画自体とapplicationのframe生成も残る。
表示中の長い文字列とCOM資源を保持する分だけメモリが増える。幅やフォントを変えた最初の描画では再利用できない。
この変更は高速な長行編集を完了したとの宣言ではなく、実測された重複計算の除去である。
