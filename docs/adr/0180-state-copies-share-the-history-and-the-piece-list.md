# ADR 0180 — 状態の写しは undo の履歴と piece の列を複製しない（履歴は塊の不変の列・piece の列は共有の束）

- 状態: 受理（設計席の決定・2026-11-11・#1451 の段 1 の調査から）
- 日付: 2026-11-11
- Issue: #1473（調査は #1451・後続は #1474）
- 規則: ARC-001 / ARC-004 / ARC-005、CPP-002 / CPP-005 / CPP-011、CNF-009、QLT-014、ADR 0009（undo の単位）/ 0044（add バッファの chunk の列）/ 0052（`Edit.restore`）/ 0056（脇のタブの不変の束）/ 0137（改訂番号）

## 文脈

`EditorState` は不変の値で、意図を写すたびに `state_ = state_.with_*(...)` で写す。1 鍵の中の写しは `l` で 3 回、`x` で 5 回、`ix<Esc>` で 12 回ある（#1451 の一時の計数）。写しの中身のうち、次の 2 つが編集の回数とともに大きくなる。

- 履歴 `EditHistory::edits_`（`std::vector<std::shared_ptr<const Edit>>`）。写すたびに件数ぶん参照数を上げ下げする。加えて `pushed` `sealed` `undone` `redone` も列を写す。
- 本文 `TextBuffer::pieces_`（`std::vector<Piece>`）。

そのため、長く編集した文書ほど 1 打鍵が遅くなる（通常モードも同じ道）。#1451 の測定では、`x` を 4,000 回した後の `lh`（編集しない鍵）が 75 → 520 µs になり、履歴を 64 件で切る一時の実験では `x` 4,000 回が 214 → 38 µs で平らになった。

## 決定

1. **状態の写しは履歴と piece の列を複製しない。** `EditHistory` の列と `TextBuffer::pieces_` は、共有の不変の束（`std::shared_ptr<const …>`）を指す。値の意味は変えない（公開の口・`size()` `position()` `revision()`・`undo()` `redo()` `applied()` の答え）。`EditorState` と `DocumentState` の側は触らない（写しが安くなるだけ）。
2. **履歴は塊の列。** 固定の件数（`history_block_entries = 256`・`EditHistory.cpp` の 1 か所）の塊（`std::vector<Entry>`）を `shared_ptr<const>` で持ち、その列も `shared_ptr<const>` で持つ。
   - 足す（`pushed`）ときに写すのは、塊の列（件数 / 256 個の参照）と、残す件数が割り切れなければ末尾の塊の頭（256 件未満の参照）だけ。redo の枝を捨てる（位置より後ろを残さない）・まとめた打鍵を畳む（末尾の 1 件を置き換える）も同じ 1 本（`kept_with`）で作る。
   - 封じる（`sealed`）・戻す（`undone`）・やり直す（`redone`）は、束を共有したまま位置と区切りと改訂番号だけを変える（列を写さない）。
   - ADR 0044（add バッファの chunk の列）と同じ考え方。
3. **piece の列は、編集 1 回につき作り直し 1 回まで。** `replaced` が新しい列を 1 回作る今の形のまま、その列を共有の束にして、状態の写しでは複製しない。piece の木（挿入が列の長さに比例しない形）は後続にする（下の「残る穴」・#1474）。
4. **`std::atomic` は使わない（CNF-009）。** `shared_ptr` の参照数は、このコードベースが既に使う形（`DocumentState` の束・`explorer_` `find_`）と同じ扱い。束は UI のスレッドだけが作り、スレッドは増やさない。
5. **undo の段数に上限は置かない。** 塊の列の余分は、256 件ごとに塊の列の中の `shared_ptr` 1 つ（16 バイト）と、塊の `make_shared` の制御ブロックと vector の頭（64 bit でおよそ 56〜72 バイト / 256 件・レビュー V-1481 の見積り）。足すたびの末尾の塊の写しは、古い値を持つ状態が消えれば解放される。

## 強制

- 単体と性質の試験 `--edit-history-property`（`tests/unit/EditHistoryPropertyTests.cpp`・既定実行の契約に載る）。
  - 塊の境（255 / 256 / 257 / 511 / 512 / 513 件）・塊をまたぐ undo / redo・undo の後の別の編集（redo の枝を捨てる）・塊の最後（index 255）と塊の頭（index 256 / 512）へ畳む打鍵・封じた後の push・空の履歴・古い値が後の push で変わらないこと・本文の写しが piece の列を共有し写した側の編集が元を変えないこと。
  - 固定 seed（1473〜1475）のランダムな push（3 つの区切り）・undo・redo・封じるの列（各 3,000 歩）と、畳む歩の多い列（各 4,000 歩・塊の頭へ畳む歩を 1 回以上踏むことも確かめる）を、毎回 `std::vector` を写す素朴な参照の模型と照合する（件数・位置・改訂番号・undo / redo の答え・適用済みの編集）。97 歩ごとに残した古い値も、最後にその時点の模型と照合する（aliasing）。
- probe `vim-lh-after-{1000,4000,16000}-edits` と `vim-x-after-{1000,4000,16000}-edits`（`tests/performance/EditedHistoryProbe.cpp`）。712 字の行で `r` を N 回（行の長さは変わらない）流した後で、`l` `h` を 100 組か `x` を 200 回流す。区間の後で `u` を数え、undo の単位が積んだ数だけあることを確かめる。N を 4 倍にしたときの費用の比で読む（ゲートには載せない）。
- 既存の性質の試験（`--text-buffer-property` の undo / redo の往復・自動退避の改訂番号）と fixture 全件。

## 結果

- 状態の写しは、履歴と piece の列について O(1)（参照 1 つ）。編集しない鍵の費用は編集の回数に比例しない。
- 1 回の push は O(件数 / 256 + 256)。新しい束のための確保は、push 1 回あたり塊の列・末尾の塊・その 2 つの制御ブロックで数個増える。代わりに状態の写し（1 鍵に 3〜12 回）ごとの列の複製と確保が無くなる。
- `TextBuffer` の値を作るたびに、piece の列の束を 1 つ確保する（編集 1 回につき 1 回）。

## 残る穴

- 編集 1 回は、まだ piece の列を 1 回まるごと作り直す（O(piece の数)）。同じ所への挿入を続ける形（`ix<Esc>` の繰り返し）では piece が 1 回に 1 つ増えるので、長い編集の後の 1 回の編集は piece の数に比例する。piece の木は #1474（読む口の二分探索は ADR 0183 の段 1・塊の列は段 2）。
- move した後の `TextBuffer` と `EditHistory` は束が null になり、読むと落ちる（前の版でも move した後の値は欄と列が食い違っていた・tidy の `bugprone-use-after-move` が使う所を止める・レビュー V-1481 の L3）。
- 行の長さに比例する分（行頭から桁を歩く O(桁)・巨大な行の全角と Tab の塊を歩く分・frame の行の写し）は #1451 に残す。

## 却下した選択肢

- **B: hot path の写しを `&&` 版（`std::move(state_).with_*`）に寄せる。** 型は変えずに済むが、変える所が意図の経路に散らばって守りにくい。`pushed` と `sealed` の O(件数) も残る。
- **C: undo の段数に上限を置く（Vim の `undolevels` の既定 1000）。** 振る舞いが変わる（施主の判断が要る）。上限の内でも 1 鍵の費用は件数に比例したまま。
- **piece の木を同時に入れる。** 広すぎる（`TextBuffer` の走査の全部と改行の索引の窓が変わる）。後続（#1474）。
