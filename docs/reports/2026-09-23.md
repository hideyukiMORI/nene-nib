## Issue #129: 実機用 Release の作成と SHA の記録をスクリプトに（実装リナ・Opus 5）

ADR 0038 の決定 5（同じ手順を 2 回モデルに踏ませたら 3 回目はスクリプト）の 1 本目。`eng/build-release.ps1 -Ref <ref>` が `eng/toolchain.ps1` で `CXX=clang-cl` を固定し、`build/release-<短い SHA>` に Ninja の Release を作って SHA-256・ref・commit・HEAD・所要時間・道具の版を `out/release/<短い SHA>.json` に記録する。**起動はしない**（起動は設計席）。
ref を名指ししない呼び方・無い ref・dirty な作業ツリーは、toolchain に触れる前に終了 1（QLT-013）。ref が HEAD と違うときだけ `build/` の下に worktree を一時的に作って build し、終わったら消すので本体の作業ツリーは動かない。既定の `build/`・`build-release/`・起動中の exe には触れない。
検証は `-Ref main`（worktree 経路・96.0 s）と `-Ref HEAD`（本体ツリー経路・104.5 s）の 2 本が終了 0、反例 3 通りが終了 1（sentinel に届かない）、`eng/test-conformance.py` 163 tests OK（160 → 163）、`eng/conformance.py` 0 violations。C++ に触れないので build / unit / symbols / 速さ / 全件は未実行。
**受け入れ条件の実測**: 2026-09-22 に手で作った `build/release-main-123/NeNeNib.exe` と、スクリプトの生成物は 978944 バイトのうち**違うのが 2 バイトだけ**だった（offset `0x80` の PE `TimeDateStamp`）。つまり「手で踏んだ手順」と「スクリプト」は同じものを作る。`/Brepro` は入れていないので、同じ commit でも作るたびに SHA はこの 2 バイトぶん変わる（SHA は「その commit の印」ではなく「この 1 回の生成物の印」として読む）。
統合単位は draft [PR #133](https://github.com/hideyukiMORI/nene-nib/pull/133)、詳細は [gate-proofs 5-ak](../quality/gate-proofs.md)。Ready・CI・merge は設計席。
