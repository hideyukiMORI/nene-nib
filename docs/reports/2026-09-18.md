## 施主決定と設計判断

- **Vim の 2 本目の範囲**は「ADR 0012 の限界 3 つを解いてからオペレータを足す」。VISUAL と画面の高さが要る移動（PgUp / PgDn・`Ctrl-d/u`・`H M L`）は engine に見えている行数を渡す形を決めてから 3 本目に。生成物の検査（#44）は Python だけで独立なので別 Issue にして並行
- **`c` に合成の効果は足さない**（削除の効果 ＋ 次の状態が INSERT）。モードは `VimState` が既に持つ。`VimEffect` を列にする案は却下（ADR 0015）
- **レジスタの本文は LF だけ**。Vim のレジスタは「行の列」で改行の形は文書の性質（ADR 0010）。engine は `line_ending()` を知らず、最終行の `dd` が足す改行の形を engine が決めると改行の正典が 2 つになる（ARC-009）。controller が `VimPutString` を写すときに `newline_of(line_ending())` に直す（`VimNewLine` と同じ 1 か所）
- **INSERT の undo 単位は `EditHistory` の中で `Edit` 1 つに畳む**（`EditBoundary::absorb`・純関数 `absorbed`）。通常モードの `coalesce` は変えない。controller が「INSERT に入ったときの履歴の長さ」を覚える案は履歴の外に第 2 の状態を持つので却下。境界は効果ではなくモードが決める（`vim_boundary()`）
- **決定 5（矢印・Home / End で単位が切れる）は維持**。oracle の `ia<Left>b<Esc>u` → `hello` は `:normal!` 1 回がまるごと 1 単位という oracle の限界で、対話の Vim は `:help ins-special-special` のとおり矢印で単位を切る。実装リナは「決定が誤り」と報告したが、出典を当たって決定どおりに。fixture には置けず単体テストで守る
- **oracle の答えが違ったら実装を Vim に合わせる**（期待値は変えない）。#22 の `dd` の回数の失敗条件（「はみ出したら何もしない」）は Vim（最終行にいるときだけ失敗）に直した
- **CI の速さの基準値は指紋ごと**（ADR 0016）。CPU 名を鍵から外して 1 つにすると世代差 47〜76% を許容に入れるしかなくゲートにならない。1 run の `--adopt` ではなく 7 run の中央値の中央値（1 試行目のコールドスタートで最大値が汚れる）。基準値の無い host で落とす `--require-reference` は保留（4 割の run を落とすのは退行の検出ではない）。機械ごとの許容も保留（同じ指紋の中は 25% に収まる）
- **「基準値が無い」は黙らない**。`Speed: no reference for <指紋> (<CPU>); recorded only -- QLT-014 is not judged on this host` を本文とまとめの 2 回。指紋が回った瞬間にゲートが黙って無効になるのは ADR 0001 の危険そのもの
- **#36 の 2 つの口は「観測できなかった試行」**で、`WindowUnavailable` に流してはいけない（打鍵ベンチの試行で使うとゲートが黙って通る）。型は `measure-speed.py` に（「試行」は打鍵ベンチの概念で `window_driver.py` は素の駆動器。実装リナの判断を採用）
- **CNF-010 の検出語は `conformance-rules.json` に**（検査器の自己検出を避ける）。正例は oracle の `header()` の出力をそのまま検査器に読ませ、書式の正本が 2 か所にあるずれを機械で捕まえる（実装リナの判断を採用）
- ADR 0016 の決定 3 の em ダッシュは ASCII の `--` に（cp932 の机で `print` が `UnicodeEncodeError` で落ちてゲートが「退行」と言う。実装リナの実測を採用し ADR の本文も揃えた）
- hide に聞くことは今日は無かった（施主決定を覆す・依存を足す・ゲートを弱める・見た目の判断のどれにも当たらない。`actions/upload-artifact` は既存の action と同じ類）

## 実測で分かったこと（規則ではなく道具の癖）

CI（`docs/quality/speed-reference.md`「CI の記録」）:

- **GitHub の `windows-2022` ランナーは host の CPU 世代が混ざる**: 16 run で 6 指紋。EPYC 7763 が 10、EPYC 9V74 が 2、Xeon 6973P-C / Platinum 8370C / EPYC 9V45 / Platinum 8573C が各 1。GPU は全部 `Microsoft Hyper-V Video`（WARP）・96 DPI
- 世代差は起動 25.9 → 38.0 ms・16 MiB 61.9 → 108.9 ms。同じ指紋の中は 1.10〜1.27 倍
- CI で退行として見えるのは `window_shown`（11〜17 ms）と `document_opened`（16 MiB で 32〜64 ms）。実機の主費用 `device_created`（NVIDIA 160 ms）は CI では 3〜4 ms
- **CI の記録は 1 つも残っていなかった**（`out/` は `.gitignore`・artifact 無し）。ログの表示行（小数 3 桁）から拾った
- CI の 1 試行目は必ずコールドスタートの外れ値（起動 240〜2408 ms）。中央値は効くが最大値は基準の記録にならない
- 16 MiB は採用値 87.349 に対し上限 109.186 で、出典の最遅（#29 の 108.886・`document_opened` 64 ms）がすれすれ
- CI の rerun は別の host に当たる（PR #48: attempt 1 が 9V45 → attempt 2 が 7763）。判定した run を作りたければ rerun
- `check.yml` の trigger に `opened` は無い（`ready_for_review` / `synchronize` / `edited` / `reopened`）。draft を経ずに開いた PR と、push と同じ秒に Ready にした PR は run が起きない → 閉じて開き直す

Vim（`docs/quality/gate-proofs.md` 5-g・ADR 0015「正直に」）:

- **行単位の回数の失敗条件**: `dd` `yy` `cc` と `dj` `dk` は最終行（最初の行）にいるときだけ失敗し、そうでなければ本文の端で止まる（`5dd` は 3 行を全部消す）
- **`:help exclusive` の 2 つの言い換え**: 行頭で終わる exclusive な移動の範囲は前の行の末尾までになり、始まりが字下げの中なら行単位になる（`dw` が空行を丸ごと消す・`db` が上の行を消す）。**`getregtype` を足して初めて見えた**（本文だけなら #22 でも一致していた）
- `op_delete` の「奇妙な Vi の振る舞い」: 複数行にまたがる文字単位の削除だけが行単位になる（`c` `y` には無い）。`$` は回数を取り、`2D` は次の行まで
- `cw` の特例は「キャレットの下に空白でない文字があるとき」で、語の最後の文字の上では 1 文字だけ（`end_word` の `stop`）
- `y` のキャレット: 文字単位は範囲の先頭、行単位は最初の行の同じ桁。空の文字単位の範囲はレジスタを書き換えない
- **oracle の限界が増えた**: 変更が 2 回ある fixture（`ddpu`）は置けない（`:normal!` 1 回 = 1 単位）。矢印で単位が切れることも測れない
- `std::string::find_first_not_of` は `memchr` を core の外へ出して ARC-003 で落ちる。走査は自前のループで
