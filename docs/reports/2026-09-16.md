## 施主決定と設計判断

- 速さは、窓が打つ節目（`input_received` / `frame_presented`）を adapters の時計で刻み、`eng/measure-speed.py` が exe を起動して 3 本のベンチを 5 回ずつ測る。基準値は `eng/perf-reference.json` に機械の指紋ごと。許容退行 25%・下限 2 ms（ADR 0011）
- **ベンチは Release の exe で測る。** 最初の実装は Debug（ASan / UBSan）を測っていて、16 MiB を開くのが 4.2 秒だった。レビューで直して 250 ms（17 分の 1）
- 描画は `InvalidateRect` → `WM_PAINT` で 1 回。まとめて来た入力は 1 フレームで描ける。200 打鍵の合計は Debug 計測で 6631 ms → 29.9 ms、1 打鍵の遅延は変わらない（3.53 → 3.55 ms）
- CI では指紋の一致する基準値が無いので記録だけ。CI の基準値は同じ CI 機の値が数回たまってから
- 設計リナのミス: ADR 0011 のファイル名に CNF-005 の禁止語 `baseline` を使い、conformance で落ちた。`0011-speed-measurement-…` に改名。**設計文書のファイル名も CNF-005 の対象**

## 実測で分かったこと（規則ではなく道具の癖）

- 施主の実機（i9-10850K / RTX 3090 / 120 DPI・Release）: 起動 → 最初の描画 191.5 ms、1 打鍵 0.906 ms、200 打鍵 2.695 ms、16 MiB を開く 249.8 ms
- **CI（AMD EPYC 7763 / Hyper-V Video＝WARP / 96 DPI）は起動 20.4 ms・16 MiB 70.1 ms。** GitHub の Windows ランナーでも窓が作れてベンチが動く。実機との差はどちらも約 170 ms で、実機の最初のフレームには GPU / DWM 側の固定費が乗っている疑い → Issue #19 で内訳を測る
- Release で測ると計測器の癖が 3 つ出た: 隠れた窓は合成器が提示を間引く（前景にして測る）、最初の 1 枚は交換鎖の暖機で遅い（暖機の 1 打鍵を捨てる）、Python の `PostMessageW` より editor がキューを空にするのが速く「まとめて post」が成立しない（窓のスレッドを止めてから post し、節目の到着幅が 50 ms を越えたら測り直す）
- `eng/conformance.py` は `機械強制: **<1 語>**` と `| ID | <1 語> |` の 1 語しか読まない。「active（実機）/ planned（CI）」のような複合状態は書けない。active にすると gate-proofs の 1-a 表に `| ID |` で始まる行が要る
- `GetWindowThreadProcessId` は返り値がスレッド ID、出力引数がプロセス ID（実装リナが計測器で取り違えて直した）
- `verify-window.py` の Ctrl+S は `SendInput` で実キーを使うので、実行中に人がキーボードを触ると本文に入る

## 残件と残るリスク

- 起動 190 ms のうち約 170 ms の所在（Issue #19）。分かるまで「爆速」は書かない
