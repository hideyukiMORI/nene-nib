入力行は `CommandInput` の3つめの値 `SearchLine`（文字列・caret・向き。補完と `ThemeCatalog` は持たない）になり、描画の経路を2本にしないために、先に入力行の見え方を `InputLineView`（プロンプトの閉じた enum ＋ 文字列 ＋ caret ＋ 候補）1つへ畳んだ（振る舞いを変えない最初のcommit）。編集の純関数は `InputText` の2本にまとめてExの `CommandLine` と共用する。

照合器は core の `VimPattern`（`magic` の部分集合。リテラル・`.`・`*`・`^`・`$`・`[...]` `[^...]`・`\<` `\>`・エスケープ・`\d \D \w \W \s \S`）で、未対応の構文は閉じた `VimPatternFailure` で拒否する。`std::regex` と `<locale>` は使っていない。走査 `vim_search` は「行ごとに0桁目から数え直し、必要な桁に足りない一致は終端（長さ0なら1文字先）まで飛ばし、位置が行の長さに達したらその行を打ち切る」規則で1回ぶんを探し、折り返したことを返す。回数は呼ぶ側が着いた位置からもう一度呼んで数える。語の境界と `*` / `#` の語は既存の文字の種類の表（`vim_character_class`）1つで切る。

engineは `VimKey` に `VimSearchPattern`、`VimEffect` に `VimOpenSearch`、`VimState` に `last_search`、`VimStep` に `notice` を足した。`/` `?` は入力行を開くだけで `VimState` を変えないので、保留中のオペレータ・回数・記録中の `.` の鍵はそのまま残る。Enterでcontrollerが `VimSearchPattern` の鍵を1回 `accept` へ送り、engineが既存のexclusiveの規則（`exclusive_range` 1か所を移動と共用）で範囲を作る。`*` / `#` は語の先頭から探すが範囲の端は元のキャレットを使い、`.` は検索を鍵1つとして記録するので追加の仕掛けなしに `d/foo<CR>.` と `d*.` が再生される。報せ（E486 / E35 / E348 / 折り返し / 未対応構文）は `vim_search_message` 1か所が文言を持ち、Exの結果と同じ `command_message` に出て次の入力で消える。IMEは入力行が開いているあいだ閉じたまま（既存の条件がそのまま効く）。UI・保存形式・schema・依存・ゲートの閾値は変更していない。

設計側（Fable）の依頼でmain `82f260d`（#84 / PR #86）から `feat/87-vim-dot-repeat` で実装した。ADR 0030を実測のあとで受理し、NORMALの直前の変更を「鍵の列」として記録して同じ `accept(VimKeyPress)` の経路へ再生する形にした。`VimState` に `recording` / `last_change`（どちらも `optional<VimRepeatRecord>` ＝ 回数1つと回数の桁を除いた `VimKey` の列）、`VimEffect` に `VimReplay`、`VimAction` に `repeat_change` を足した。記録の確定・破棄は `vim_step` の後段にある純関数1か所だけが書き、鍵の意味ではなく前のモードと効果で分ける。controllerは前後で履歴を閉じて鍵を1つずつ流すだけで、`.` は記録されないので再帰は深さ1で止まる。UI・IME・描画・保存形式・schema・依存・ゲートは変更していない。

実装の前に固定Vim 9.1を201ケース起動して決定を確かめた（`probe.py` 172 ＋ `probe2.py` 29）。決定2（回数の積を1つに畳む。`2d3w5.` と `6dw5.` が同じ5語）、決定4（`ifoo<Home>bar<Esc>.` は `bar` だけ。`<End>` / `<Left>` / `<Down>` / `o` からの挿入も同じ）、決定7（`x3..` などが回数3を引き継ぐ）は一致した。Vimソースは読んでいない。

決定5だけがVimと違う。Vimは `vlld.` を同じ大きさの範囲で再生し、`xjvlld.` でもVISUALの削除を繰り返すが、本実装は直前の変更を消して何もしない（ADRが安全側を選んでいる）。fixtureには採らず、[Issue #91](https://github.com/hideyukiMORI/nene-nib/issues/91)へ送った。

決定3も当初は「Vimは失敗したオペレータで記録を入れ替える」と読んだが、これは測り方の誤りだった。失敗してビープする命令のあと `:normal!` の残りの鍵は捨てられるので、`xdkj.` では `j` も `.` も実行されていない（最終カーソルが1行目のままなのが実測の証拠）。鍵を命令の切れ目で区切って測り直すと（probe3 28件・probe4 21件×2形）、取消になった命令は自分の鍵を捨てるだけで直前の変更を変えず、決定3と一致する。範囲の作れない `dk`/`dj`/`2dd`/`2D`、回数の入らない `3r`、外れた `f`/`;`、motionでない `dq`、`g` の続きが無い `dgz`、失敗した `yk`、Escの取消のいずれも同じ。engineは変更していない。ビープする命令の後ろに鍵が続く列は既存の1回 `:normal!` の生成器では測れないので、ビープしないEscの取消2件だけをfixtureに採り、残る12経路は `--vim-dot` の対象unitが直接確かめる。

実装の途中でADR 0028の範囲外の穴が出た。`N.` が挿入命令を繰り返すには `3ifoo<Esc>` が `foofoofoo` でなければならないが、回数付きの `i a I A` は回数を捨てていた。既存の `VimInsertRepeat` を `entered_insert` でも立てて塞ぎ、`counted-insert-*` 5件で固定Vimとの一致を確かめた。これに伴いcontrollerの `interrupt_vim_insert`（外からの割り込みで入力記録を捨てる）と `perform(VimMoveTo)`（Vimの鍵による移動で履歴だけ閉じる）を分け、入力記録を捨てる判断はengineの1か所に残した。

採用fixtureは99件でfixtureは551→650。`--only dot- --only counted-insert-` の部分再生成で99件だけを測り、既存551行は逐語再利用した（削除行はmetadata 2行のみ・先に採った97行は再測定でも同じ値）。`--vim-dot` は新規99＋共有境界8件（o/Oの回数反復・r・f/t・g待ち）と、記録の確定/破棄・回数の折り畳みと置換・`.` が `.` を記録しないこと・undo 1単位とredo・CRLFの保存bytes・1行の表示領域での再生・VISUALの変更が記録を消すこと・INSERTの `.` が文字であることと取消12経路を確認して909 checksすべて成功。ADR 0028の入力記録に触れたので `--vim-open-lines` / `--vim-open-line-external` / `--vim-open-line-recovery`（565 / 46 / 430）と、次キー待ちをまたぐ `--vim-replace` / `--vim-character-search` / `--vim-line-jumps`（460 / 621 / 989）も実行し、すべて成功。`vim_step` の後段を全Vim経路が通るためunit全体も1回だけ実行して7181 checks成功。初回buildは `commanded` と `visual_acted` が60行上限を超えて拒否され、巻きをNORMAL/VISUAL共通の `scroll_action` にまとめ `.` を `history_action` に寄せて修正した。閾値・除外・重大度は変えていない。symbols 2libs/0、conformance 0、formatも成功。コマンドと証拠は [gate-proofs 5-v](../quality/gate-proofs.md)。

性能は測っていない。1打鍵あたり小さな `vector` の複製が増えるが、予算0.9 msに対する影響は速さのゲートが見張る（ADR 0016 / 0021）。computer-useによる実機の画面確認は未実施で、起動中の旧版PIDには触れていない。成果物は `build/issue87/NeNeNib.exe`、SHA-256 `19952fcabafd0f1885c2a732802ec89b1ea238f651722e401e0e8371769da068`。CMakeの一時出力先は既定へ復元済み。
