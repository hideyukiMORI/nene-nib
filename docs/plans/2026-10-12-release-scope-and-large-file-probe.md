# 初版の対応範囲案と大容量編集の成立性試験

2026-10-12 / Issue #440 / [正式リリースのロードマップ](2026-10-11-release-roadmap.md)の段階0と、段階1の事前計画。

hideの開始指示に従って再開する。入力サイズの目安は**2GiB（2,147,483,648 bytes）**、構文色は**Python・JavaScript・TypeScript・JSON・Markdown・C・C++**を優先する、という回答を反映した。2GiBは試作の入力目安であり、現製品の対応保証ではない。製品上限・行長等の制限は結果を見て明示する。

以下の「初版案」は作業の切り分けであり、SPECIFICATIONや受理済みADRを置き換えない。見た目、所有・並行性・保存形式の変更は、各実装前の設計で決める。旧split総2msのholdと既存性能ゲートも変更しない。

## 現行コードから分かった制約

調査基準はmain `5c782f8`。この調査で大容量を実測したわけではない。

| 正典経路 | 現在の形 | 試作で解くこと |
| --- | --- | --- |
| `EditorController::read_document` / `FilePort::read` | 64MiB上限、UIスレッドで同期、所有文字列を受け取る | 上限だけを変えず、操作を止めない要求/完了と、寿命のある読み取り専用の本文を扱う |
| `Win32FileAdapter::read_all` | サイズ確認後に全文の領域を確保してReadFileへ渡す | 読込範囲を限ったI/Oまたはメモリマップ、短い読込・末尾・不正な文字コードの扱い |
| `TextBuffer::from_validated_utf8` | 所有文字列と全文の改行位置列を作る。編集後の本文はpiece tableで共有する | 既存TextBufferを正本にして、本文の大量コピーを避け、索引作成と移動の費用を制御する |
| `EditorController::save_document` | `text()`で全文をまとめ、文字コード変換後にFilePortへ渡す | 本文の不変な版から順に書き出し、保存中の編集と保存済み位置を区別する |
| `Win32FileAdapter::write` | 32MiBずつ書くが入口は全文。Flush後に同じフォルダの一時ファイルから置換する | 一時ファイル/置換の安全性を保持し、全文の一時文字列を不要にする |
| `Win32Worker` / 完了通知 | 固定ワーカー1本とキュー。型付きportで要求・回収し、窓メッセージは合図だけ | 索引・読込・保存を短い仕事に区切り、取消・古い結果・別タブとの競合を扱う |
| `VisualTextView` / `BodyTextLayouts` | 表示位置に必要な論理行を共有文字組みへ渡す。変更行全体の文字組みは残る | ファイル容量と論理行長を分けて評価する。表示だけを別の本文/幅計算にしない |

メモリマップの所有、元ファイルの外部変更・置換と保存、UTF-8の検証完了前の表示、索引の未完成状態は設計論点として残す。core/applicationへファイル・時刻・スレッドを持ち込まず、adapterの所有と不変な結果で解く。保存中の本文を変更できる場合、保存した版だけを保存済みにし、その後の入力を未保存のまま残す。

## 段階1の試作の区切り

1. **A: 本文・索引・読み書き。** 公開契約と所有をADRに定め、既存TextBuffer/FilePortの正典経路へ接続する限定試作を作る。まず画面なしで、読込・移動・局所編集・undo/redo・保存・再読込とメモリを確かめる。試作専用の第二のエディタや保存処理を作らない。
2. **B: 応答性。** Aの内容一致と失敗時の保持を確認した版で、固定ワーカーと実際の窓に接続する。大容量処理中の別タブ操作、取消、古い完了の破棄、入力→提示を確かめる。新しい見た目が必要ならD12の設計を先に行う。
3. **判定。** 成立した操作と失敗を記録し、段階2の製品対応へ進むか、所有・索引・I/Oを見直すかを選ぶ。Aだけの成功で入力応答や2GiB製品対応を宣言しない。

新しいAPI・所有・並行性のADRと試作差分は次の焦点Issueで扱う。この計画の保存を実装済みや測定許可の代わりにしない。実画面・性能測定は、準備した版・条件・所要時間を示してhideの他案件と時間帯を調整する（ADR 0114）。

## 試験入力と操作を先に固定する

GiB/MiBは2の累乗。生成器は小さな固定ブロックを順に書き、全文をメモリに作らない。乱数・実ユーザー文書は使わない。生成式、行数・最大行長・BOM/改行、実bytes、SHA-256、編集地点をmanifestへ残し、最初の測定前のcommitで固定する。

| 入力 | 大きさ | 内容と狙い |
| --- | ---: | --- |
| C16 | 16,800,000 bytes | 既存の大きなファイル用ベンチと同じUTF-8/CRLF/200,000行。通常サイズの対照 |
| L1 | 1GiB + 1MiB = 1,074,790,400 bytes | BOMなしUTF-8、512 bytesのCRLF行。日本語・ASCIIを含め、1GB超と通常の多数行を確かめる |
| L2 | 2GiB = 2,147,483,648 bytes | BOMなしUTF-8、128 bytesのLF行。16,777,216個の改行を持ち、索引のメモリと末尾への移動を確かめる |
| L3 | 2GiB = 2,147,483,648 bytes | UTF-8 BOMを含む。LF/CRLF混在、日本語、最大64KiBの行を含め、末尾改行なし。容量と行長を分けて確認する |
| E | 小さな境界入力と8MiB長行 | 空、BOMだけ、UTF-8の多バイト境界、CRLFの区切り、末尾の不正UTF-8、改行なしの8MiB行。長行の応答は別記し、2GiBの全行長を保証した扱いにしない |

L3の行配置、Eの全bytesと期待結果は試作のfixture実装時にmanifestへ列挙し、実測前に固定する。BOM・改行も表の総bytesに含める。測った後に都合のよい生成式や行長へ替えない。

各C16/L1/L2/L3で実施する操作は次の1本に揃える。

1. 新しい隔離profileで開き、先頭・1/2付近・末尾の内容と位置を照合する。総行数が未確定の間の動作も記録する。
2. manifestのUTF-8境界に置いた3地点で、ASCII/日本語の挿入、削除、改行を含む置換を行う。1操作の挿入/削除は最大4KiB、編集地点はバイト位置と期待文字列の両方で固定する。
3. 全操作をundoして元のbytesへ戻ることを照合し、redoして編集後の期待値へ戻す。
4. 別名保存と、試験用複製への同名保存を確認する。2GiB入力への挿入で一時的に2GiBを超える場合も扱い、読込上限と保存・内部位置の表現を混同しない。
5. 保存結果をストリーミング照合し、再読込後の3地点・行境界・未保存状態を確認する。BOM、混在改行、末尾改行なしもそのまま比較する。

期待値は編集の指示列を使う独立したストリーミング参照で作り、製品の保存結果同士を比べただけで正しいとしない。元入力・期待値・実出力のSHAとサイズを残す。元入力は書き換えない。

失敗系は読み取り不能、短い読込、書込途中/Flush/置換の失敗、取消、古い完了、保存中の追加入力を対象にする。まず小さな入力と注入した失敗で確認し、実ディスクを満杯にする試験はしない。実ファイルの確認では隔離した試験ファイルだけを使う。取消・失敗時は元ファイルと未保存の本文を保持し、保存成功として扱わない。

## 測定の境界・回数・失敗の扱い

対象機は現在のWindows実機（i9-10850K、物理メモリ約64GiB）。入力・出力はD:/NeNeNib配下の同じボリュームに置く。実行時にOS/機器/空き容量/負荷、commit・exe SHA・Releaseのビルド記録、profile・入力manifestのSHAを記録する。D側の結果をC側の速度保証へ読み替えない。

| 記録するもの | 開始と終了、解釈 |
| --- | --- |
| 最初に読めるまで | 開く要求→先頭の表示可能な本文。Aの値は本文の準備まで、Bは最初の描画提示までとして分ける |
| 索引・移動 | 索引要求→要求範囲の利用可能、途中/末尾への移動要求→該当本文の利用可能。先頭表示と全索引完成を一つの時間にしない |
| 局所編集・undo/redo | 各要求→次の本文状態。Bでは入力受信→描画提示も別に記録する |
| 保存・再読込 | 保存要求→Flushと置換が成功するまで、再読込要求→該当本文が利用可能になるまで |
| メモリ | プロセスのprivate bytesとworking setの開始値・高水位・終了値、本文/索引/編集分の所有量。マップした仮想領域・常駐量・私有コピーを区別する |
| 背景処理との併用 | 開く/索引/保存の各処理中に別タブで入力し、入力→提示、応答の最長停止と取消要求→終了を記録する |

Aの正常系はC16/L1/L2/L3を各3回、新しいプロセスで固定順C16→L1→L2→L3、逆順、正順の計12回。起動ごとにprofileと出力を分ける。OSのキャッシュは消さず、初回と後続を区別して全値・中央値・min/maxを示す。3回から有意差や一般的なp95を主張しない。

BはC16とL2へ絞り、各3回。各回の読込/索引/保存の稼働中と処理後を区別し、別タブで1打鍵ずつ次の描画提示を待つ固定20打鍵を送る。途中で仕事が終わった試料は「稼働中」に混ぜない。各群の件数・全値・中央値・最大値と、長い停止を記録する。小ファイルの性能退行は直接影響する既存ベンチだけで確認し、既存基準値・許容は変えない。

失敗系/Eは対象ごと1回の決定的な契約確認。内容不一致・アクセス違反・保存元の破損が出たらその時点で測定を止める。1操作300秒を監視上限とし、超えたら未成立として未完了の記録を残す。試作は試験用ファイルだけを触り、停止後の一時ファイルは記録・内容確認してから整理する。

外れ値は除外せず、失敗・欠測・背景処理が先に終わったものも保存する。都合のよい試料を得るための再試行はしない。欠陥を直して再実行する場合は、旧結果と原因を保持し、変更版・対象・回数を次の測定前に固定する。試験器自体の固定前の小さな動作確認と、固定後の本測定を混同しない。

## 成立性の判断と未決点

次へ進む必須条件は、(1)全文内容の一致と失敗時の保持、(2)2GiB入力で全文コピーを繰り返さない所有・保存経路、(3)索引/長行/背景処理の費用が分かり、応答を止める箇所を特定できること。Aで実現できてもBが未確認なら「画面なしの成立性まで」と記録する。全行長・全文検索・大量置換・2GiBのShift_JISの保証には広げない。

試作の判断条件は、2GiB入力と最大4KiBの局所編集でprivate bytesの増分512MiB以内（入力サイズの1/4）、Bの別タブの入力→提示と取消の最長停止100ms以内とする。マップのworking setは別記する。これは全文コピーと長い操作停止を見逃さないための今回の試作条件で、既存ゲートや製品の性能保証を変更しない。ファイルの開閉・保存総時間はまず実値を示し、この段階で任意の合格秒数を約束しない。

splitの新しい採用条件は2026-10-12にhideが採用した（D45・[ADR 0120](../adr/0120-split-acceptance-is-relative-and-tail-bounded.md)）。既存の単画面ゲートを維持し、同条件の単画面との入力→提示の中央値の増分を`max(1ms, 単画面中央値の25%)`以内、分割時のp95を16.7ms以内とする。独立文書と同一文書を分け、各100打鍵の固定試行で絶対値・差・分布・メモリを記録する。p95は昇順の95番目、中央値は50/51番目の平均。旧総2msの結果を合格へ変更しない。条件だけの採用であり、製品採用と実測は未了。比較対象・本文・表示条件・測定器・試行順を具体化して事前commitへ固定し、実機の時間帯を調整してからsplit試験を再開する。

段階0で得たものは、容量・言語の優先指定と初版の範囲案、現状の制約、A/Bの限定試験計画とsplitの新しい採用条件である。段階1Aの最初の単位として#442・[ADR 0119](../adr/0119-utf8-save-borrows-piece-segments.md)でUTF-8保存を本文断片の同期借用へ接続した（[契約確認](../quality/chunked-save-2026-10-12.md)）。改行索引#446 / PR447は対象契約を確認済みだが実機性能未成立でdraft。2026-10-12 20:47のhide指示で試験を保留し、#450で[元本文の所有・範囲取得・保存版の設計案](../design/2026-10-12-large-file-source-ownership.md)を先行する。次は分割検証と読込境界のADRを具体化する。64MiB上限と同期I/Oはまだ残り、A/Bの成立性試験は未実施。設計案をAPI採用や2GiB製品対応とは扱わず、試験の再開時期はhideと調整する。
